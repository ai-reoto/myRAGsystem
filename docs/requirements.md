# RAGシステム 要件定義（v1.1）

## 1. 背景・目的
### 1.1 背景
- ナレッジがMarkdown/PDF/テキストに分散し、検索コストが高い。
- LLM単体回答は最新情報や社内固有情報に弱く、根拠提示も不十分。

### 1.2 目的
- 社内/個人ナレッジを対象に、根拠付きで回答できるRAG（Retrieval-Augmented Generation）を構築する。
- 回答品質・速度・運用性の最低基準を定義し、MVPから段階的に改善する。

## 2. スコープ
### 2.1 対象（In Scope）
- 文書取り込み（`.pdf`, `.md`, `.txt`）
- 前処理（正規化、チャンク分割、メタデータ付与）
- ベクトル検索（Top-K + メタデータフィルタ）
- 回答生成（取得根拠をコンテキストとして利用）
- 回答時の引用表示（文書名・該当箇所）
- 最低限の運用ログ（問い合わせ・検索結果・応答時間）

### 2.2 非対象（Out of Scope: 初期フェーズ）
- OCR（画像/スキャンPDF）
- 音声入力・音声応答
- 厳密な文書ACL/テナント分離
- エージェント型ワークフロー（ツール実行連鎖）

## 3. ステークホルダー
- 利用者: 開発者、業務担当者
- 管理者: システム管理者（文書投入・監視）
- オーナー: プロダクト責任者（要件優先度決定）

## 4. ユースケース
1. ユーザーが自然言語で質問する。
2. システムが関連チャンクを検索する。
3. LLMが取得根拠に基づいて回答する。
4. ユーザーが引用元を確認する。
5. 管理者がログを確認し、精度改善を行う。

## 5. 機能要件（FR）
| ID | 要件 | 優先度 | 受け入れ条件 |
|---|---|---|---|
| FR-01 | 文書取り込み（バッチ） | Must | 指定ディレクトリから `.pdf/.md/.txt` を登録できる |
| FR-02 | 文書更新時の再インデックス | Must | 更新文書のみ再処理できる |
| FR-03 | 類似検索（Top-K） | Must | 質問ごとに関連チャンクをK件返せる |
| FR-04 | 回答生成 + 引用表示 | Must | すべての回答で1件以上の引用を返す |
| FR-05 | 監査ログ | Must | 質問・取得チャンクID・回答・遅延を記録 |
| FR-06 | メタデータフィルタ検索 | Should | 文書種別/日付で絞り込み検索できる |
| FR-07 | 管理用再取り込みAPI | Could | 指定doc_id単位で再取り込み可能 |

## 6. 非機能要件（NFR）
| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 性能 | p95応答時間 8秒以内（質問→回答） |
| NFR-02 | 同時性 | 同時10ユーザー（PoC目標） |
| NFR-03 | 可用性 | 月間稼働率 99.0%以上（PoC） |
| NFR-04 | セキュリティ | APIキーは環境変数/シークレットで管理 |
| NFR-05 | 通信 | 外部通信はTLS前提 |
| NFR-06 | 可観測性 | 構造化ログ（JSON）で追跡可能 |

## 7. 品質KPI（MVP時点）
- 回答妥当性（人手評価）: 代表質問10件で70%以上
- 引用付与率: 100%（全回答に1件以上）
- 再インデックス反映時間: 小規模文書群で10分以内

## 8. 前提・制約
- モデルAPI利用のため外部ネットワークが必要。
- 初期は単一言語（日本語中心）を対象。
- データ量は中小規模（~数万チャンク）を想定。

## 9. リスクと対策
- ハルシネーション: 「根拠がない場合は不明と回答」プロンプトを適用。
- 検索精度不足: チャンクサイズ/オーバーラップ/Top-K をA/B評価。
- コスト超過: 埋め込み更新頻度とモデル選定を段階最適化。
- 運用負荷増大: 失敗ジョブ再実行とログ可視化を先行導入。

## 10. 未決事項
- 埋め込みモデル/生成モデルの最終決定
- ベクトルDB（Chroma / pgvector / FAISS）の最終選定
- 認証方式（ローカル認証 or SSO）
